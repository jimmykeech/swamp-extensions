# @jamesakeech/technitium

A [swamp](https://github.com/swamp-club/swamp) extension for managing
[**Technitium DNS Server**](https://technitium.com/dns/) — zones, records,
block and allow lists, cache, diagnostics, settings backup and restore, and
cluster membership.

One model type: **`@jamesakeech/technitium`**. One instance is one DNS server.
A cluster is two instances, because most operations are node-local and the two
nodes can and do disagree — which is usually the thing you need to see.

This was written while migrating a live authoritative pair between
hypervisors, and its shape comes from what that exposed rather than from
reading the API docs. Three of those findings are the reason it exists.

## `record_ensure` — the upsert the API cannot express

Technitium has no upsert. Verified against a live server:

|                 | record exists                 | record absent                    |
| --------------- | ----------------------------- | -------------------------------- |
| `record_add`    | fails, "record already exists" | creates                          |
| `record_update` | updates                       | fails, "zone ... does not exists" |

That makes both unusable in a re-runnable workflow step. `record_ensure` adds
when absent, updates when the value or TTL differs, no-ops when already
correct, and reports `created | updated | unchanged` per record. It fans out
over an array in one execution rather than taking the per-model lock N times.

It works for **every** record type. That sounds unremarkable until you try to
write a TLSA.

## The read/write asymmetry

Technitium does not use the same field names to read a record and to write it,
and it does so **only for some types**. A TLSA reads back as:

```json
{ "certificateUsage": "DANE-EE", "selector": "SPKI",
  "matchingType": "SHA2-256", "certificateAssociationData": "7B96..." }
```

…but must be written as `tlsaCertificateUsage`, `tlsaSelector`,
`tlsaMatchingType`, `tlsaCertificateAssociationData`.

Feed the read shape back in and the write is rejected. Compare the two shapes
after a write and they never match — which is how a successful write comes to
report failure, and why the honest reaction mid-cutover (retry it) is the
wrong one.

`SSHFP` and `URI` diverge too; `SVCB` and `HTTPS` do not. And the sharp edge:
**`SRV` writes `priority`/`weight` bare while `URI` writes
`uriPriority`/`uriWeight`** — same read names, different write names. A single
global rename would silently corrupt one of them, so the mapping is keyed by
record type. Both name sets were taken from the server's own `js/zone.js` at
v15.4 rather than inferred.

You can pass `rData` in **either** shape. They normalise to the same record,
hash to the same data instance name, and compare equal.

## What a settings backup does not contain

`settings_backup` includes every section by default, including `dnsSettings`
and `logSettings`. Getting that wrong is not loud: a backup missing
`dns.config` has no forwarders, no server domain and no cluster catalog, and
nothing about the result tells you so — a "full" backup and a config-only one
can come back byte-identical.

Even complete, a backup carries none of the following, because Technitium
treats them as node-local identity rather than shared config:

- **`webservice.config`** — the TLS enable flag and HTTPS port. A restored node
  comes up with TLS off and its cluster port closed. Fix with
  `web_service_set_tls`.
- **The web service certificate.** Self-signed certs are generated by the
  server, so a rebuild mints a **new** one and any TLSA record pinning the old
  key is stale. Repin it before expecting a cluster to re-form.
- **Cluster membership.** There is no `cluster.config` on disk at all; a
  restored node reports `clusterInitialized: false` however complete the
  backup. Use `cluster_init` and `cluster_join`.

Plan a rebuild around those three or it will look like the restore failed.

## Cluster

`cluster_state` reports membership as **one node sees it** — worth calling on
both, because a secondary reporting the primary `Connected` does not mean the
primary believes it is in a cluster at all.

`cluster_init` **mints a fresh shared secret** and cannot adopt an existing
one, so it orphans any secondary still holding the old one. Run it only when
prepared to rejoin every secondary.

`cluster_join` authenticates against the **primary** with a username and
password — not an API token — and its `primaryNodeUrl` must carry the primary's
**domain name**. Technitium rejects an IP outright, correctly: the node
presents a certificate for its cluster name, which an IP URL could never match.
It also refuses to run while a catalog zone exists on the joining node, so
delete that first — the `SecondaryCatalog` copy on the secondary, never the
`Catalog` on the primary.

The destructive half of the cluster API — `secondary/leave`,
`primary/deleteSecondary`, `primary/removeSecondary` — is deliberately **not**
wrapped. Those tear down a working cluster and nothing in a workflow should
reach them.

## Verification status

Paths, parameters and response shapes were read from the server's API and its
UI JavaScript at v15.4, not guessed. But *ported faithfully* is not
*exercised*, and the difference is worth stating.

**Verified against a live pair:** `zone_list`, `record_list`, `record_get`,
`record_add`, `record_ensure`, `record_update`, `record_delete`,
`settings_get`, `settings_backup`, `cluster_state`, `blocking_get_settings`,
`allowed_*`, `blocked_*`, `cache_list`, `cache_delete`, `dashboard_stats`,
`client_resolve`, and `logs_query`'s not-installed error path.

**Not exercised**, because running them means causing the outage or state
change they exist to cause: `zone_create`, `zone_enable`, `zone_disable`,
`settings_restore`, `web_service_set_tls`, `cluster_init`, `cluster_join`,
`cache_flush`, `blocking_set_state`, `blocking_temporary_disable`,
`blocking_set_lists`, `blocking_force_update_lists`,
`dnssec_validation_set`. Every one of those was performed successfully during
the migration this was written for, but through predecessor code rather than
this file. Exercise one on something disposable before relying on it.

## Setup

```yaml
globalArguments:
  baseUrl: http://192.0.2.10:5380
  apiToken: '${{ vault.get(my-vault, technitium-api-token) }}'
```

Use an **IP**, not a name. A DNS server that has to resolve its own name to be
reachable is a circular dependency, and it bites exactly when the server is
unhealthy.

The token needs rights for the methods you call; the cluster methods need
**Administration**. In a cluster, auth config replicates — a token minted on
one node authenticates on its peer within seconds, and revocation propagates
the same way, with the same short lag. If a revocation looks like it failed to
propagate, re-check before concluding it did.
